# Vince TEE — original Keymaster compatibility audit (2026-11-09)

**Purpose:** Diagnose a systemic application-compatibility bug, not to fabricate
attestation or claim that an unlocked custom-ROM phone has authentic verified
boot. **Device testing is still required. No one can guarantee all security-
restricted apps will accept this Android 13 custom ROM.**

## What the source demonstrates

1. AlwaysStrong Inject v1.0.5 upstream history pinned at
   `54c2a70552bc477436e157fd3c6cbd8d43c0e897`:
   `module/build_target_txt.sh` automatically adds all third-party packages
   to `/data/adb/tricky_store/target.txt` unless WebUI `auto_target=0`.
   GMS / GSF / Vending remain forced `!` in both cases.
2. TEESimulator-RS v6.0.1-308 (PR76 code), `ConfigurationManager.kt`:
   `AUTO` mode resolves to `GENERATE` when
   `DeviceAttestationService.isTeeFunctional` is false.
3. `KeyMintSecurityLevelInterceptor.kt`, `handleGenerateKey`:
   `ConfigurationManager.shouldGenerate(callingUid)` forces
   `doSoftwareKeyGen()`, even if there is **no attestation challenge**.
   Thus a failure of *hardware attestation* can cause a non-attested AES/HMAC
   or RSA/EC key that **could be generated by the original Keymaster** to be
   software-generated instead. Applications may then receive unexpected
   authorizations, persistence, user-auth behavior or hardware-backed status.
4. This new branch patches only this non-attestation dispatch: when no
   attestation challenge, dedicated attestation key, attest-key purpose or
   device-ID request exists, forward `generateKey` to the original Keymaster
   instead. Clear the prior synthetic/cert cache for the regenerated alias to
   avoid a split on the next `getKeyEntry`.
5. Existing attestation requests still follow v308 dispatch (including MGF1
   SHA-1 fix). All existing module content, including keybox, native
   libraries, Zygisk Inject, module.prop and configuration, is preserved
   **byte-for-byte** in the engineering artifact; only `tee_classes.dex`
   differs. No kernel modification.

## Validation

- Patch fails closed if source layout or known AUTO fallback changed.
- All source unit tests and per-file ZIP preservation tests must pass.
- GitHub Actions compiles pinned upstream v308 source and verifies a unique
  bytecode marker in `classes.dex`.
- The previous PR76 module ZIP is sha256-pinned:
  `5d1bd0ee2130674786752d9e2cf9fb9f01b3967f0a605b96adb670309a0befdb`.
- The repacker only changes `tee_classes.dex` and adds a prominent notice.
- **No on-device ADB, KeyMint, crash-app, Play Integrity or Duck Detector
  success is claimed.**

## Non-invasive option already available in current official module

In AlwaysStrong WebUI, toggle **Auto targeting = OFF**, use module **Action**
to rebuild target.txt, and reboot. The builder then removes automatic targeting
of third-party apps while retaining the three forced Google packages.
Custom per-app overrides must be checked separately. This may improve
compatibility by letting apps reach genuine Keymaster and avoids a new flash,
but apps requiring authentic attestation can still reject the ROM.

## Real limits

- A software-generated attestation chain is not genuine on-chip verification
  of bootloader lock, the TEE manufacturer, or a trusted Android install.
- Passing Google Play Integrity or Duck's LOCAL chain evaluation is distinct
  from an app accepting a cryptographic key or its own app-specific policy.
- Prior four Duck reports all displayed `TEE CLEAR`, but explicit RSA-OAEP
  MGF1 subtests were marked `skipped`; `Keystore2: Unexpected reply` was
  reported. They contain no target-app `FATAL EXCEPTION` stack trace.
- The persistent SELinux timing anomaly is explicitly experimental and is
  not justification for weakening the SELinux policy.
- Never publish keybox.xml private keys or recovered application credentials.
- Back up existing app data and module ZIPs before any test; a change in the
  origin of a cryptographic key could invalidate data originally encrypted
  with a now-replaced key.
